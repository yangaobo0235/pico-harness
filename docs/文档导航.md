## 怎样维护

1. **先找主题，再改章节。** 命令改助手使用；字段和状态路径改配置与状态；模块与依赖改架构；启动命令改本地开发；发行与恢复改运行维护。其他位置引用该主题，避免复制规则。
2. **描述当前能力。** 写清适用条件、操作、预期结果及失败后的下一步。删除被替代的说明；不把开发流水、待办和验收日志追加成正文。
3. **控制文档数量。** `docs` 的目录和文件名使用中文，技术标识保留在正文中。一次需求、重构或缺陷通常不新增方案/总结。只有读者任务独立、内容长期有效且现有主题容纳不合理时才新增；失效主题可合并或删除。
4. **计划留在本机。** 临时计划与执行证据放 Git 忽略的 `.pico/plans/`、`.pico/` 或仓库外测试目录，长期结论维护在正式主题中。新克隆可按需创建计划目录，正式文档不依赖本机计划链接。
5. **代码和文档一起完成。** 检查变更是否影响命令、配置、状态格式、接口、模块职责、安装产物或运维流程，更新对应文档；纯内部修复无需机械修改文档。PR 说明更新了哪篇，或为何无需更新。
6. **示例可验证。** 仓库引用使用相对链接，示例脱敏，命令从指定目录可执行。区分受控回归、实际平台安装和真实外部链路；不把跳过或未执行写成通过。

文档链接检查：在仓库根目录执行 `uv run python -m scripts.ci.check_docs`。不要求给每篇文档追加变更日志或每次修改更新时间。
